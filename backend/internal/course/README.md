# 课程数据模型与教学班（合班）设计

> 本文档面向后续开发者，说明课程管理的数据模型与**设计理由**——重点是教学班
> 这一层的引入背景。字段以建表 SQL 为准，路由以 OpenAPI 生成物为准，文件归属
> 以代码为准；本文只写「为什么这样设计」与不易从代码直接看出的约束语义。

## 1. 概述：课程三层结构

课程数据分为三层，自上而下：

| 层 | 表 | 中文 | 说明 |
|---|---|---|---|
| L1 | `course_catalog` | 课程库（抽象课程） | 课程的元信息，如「高等数学」「MATH101」，不含学期/教师 |
| L2 | `course_offerings` | 开课 | 某课程在某学期、由某教师、面向某教学班的一次开课 |
| L3 | `course_sessions` | 课次（上课实例） | 某开课在具体某天、某教室、某节次区间的一次上课 |

关系链：`course_catalog 1—N course_offerings 1—N course_sessions`。

L2「开课」是承上启下的关键：它把一门抽象课程、一个学期、一位教师、一个授课群体绑定在一起。**「授课群体」就是教学班。**

## 2. 为什么引入「教学班」

### 2.1 旧模型的问题

早期 `course_offerings` 用一个自由文本字段 `class_name`（如「计科2201」）表示班级，且唯一约束为 `UNIQUE(catalog_id, semester)`——即同一课程同一学期只能开一次。

这无法表达两类常见场景：

1. **合班**：一门课由多个行政班**在同一时段、同一教室**一起上。例如「高等数学」由「计科2401 + 计科2402」合班上课。旧模型只有一个 `class_name` 字符串，无法结构化表达「多个行政班」，也无法保证引用的行政班真实存在。
2. **同教师同学期面向不同群体分次开课**：例如高数老师上午给 1+2 班上一组、下午给 3+4 班上一组。旧模型的 `UNIQUE(catalog_id, semester)` 会把这两组视为重复而拒绝创建。

### 2.2 教学班的定义

引入**教学班（teaching class）**：一个**命名的行政班集合**，代表「被一起授课的一组行政班」。

- **行政班（admin class）**：持久的学生编制，由 `年级 + 名称` 标识，如 `2024级 / 计算机244`。属于用户/人员管理模块（组织单元，不是课程概念）。
- **教学班（teaching class）**：若干行政班的命名组合（合班），如「高数-A班（1+2）」= {计算机241, 计算机242}。

一次开课（L2）面向**恰好一个教学班**。于是：

- **合班** = 教学班包含多个行政班成员，同一时段、同一教室一节课由一个教学班（多成员）承载，天然成立。
- **同教师同学期分群体开课** = 两个不同教学班 → 两次开课。唯一约束为 `UNIQUE(catalog_id, teaching_class_id, semester)`，两组互不冲突。

### 2.3 场景示例

> 高数老师同一学期：上午给「计算机241 + 计算机242」上课，下午给「计算机243 + 计算机244」上课。

建模：

- 行政班：计算机241、计算机242、计算机243、计算机244
- 教学班 A「高数-上午」= {241, 242}；教学班 B「高数-下午」= {243, 244}
- 开课 1：高数 / 教学班 A / 张老师 / 2026秋
- 开课 2：高数 / 教学班 B / 张老师 / 2026秋

两次开课因 `teaching_class_id` 不同而满足唯一约束；各自的课次（L3）落在不同时段/教室，互不冲突。

## 3. 数据表

建表 SQL 以 `internal/user/org_store.go`（组织三表）与 `internal/course/store.go`（课程三表）的 `Migrate` 为准，此处不重复列字段。两个不易看出的语义：

- **`course_catalog.code` 是身份键**（NOT NULL UNIQUE，教务处课程代码）：`name` 可重名（同名不同码是合法形态），导入器按 code upsert，开课/课次按 code 解析引用。课程库身份键曾经历 `name` → 可空 `code` → `code NOT NULL` 三个阶段，当前为最终形态；**部署新版本前必须删库重建**（`Migrate` 只 `CREATE IF NOT EXISTS`，不升级旧库），详见 `store.go` 中的警告注释。
- **`course_sessions` 是节次区间** `[period_start, period_end]`：连上多节（如 3-4）是**一个课次实例**，不逐节展开；区间重叠无法用唯一索引表达，由应用层校验（见 §4）。

## 4. 关键约束与逻辑外键

- **无数据库级 FOREIGN KEY**。所有跨表引用（`catalog_id`、`teaching_class_id`、`offering_id`、`classroom_id`）均为逻辑外键，由应用层校验存在性——与项目既有约定一致（见 `AGENTS.md` 的 MySQL 幂等迁移模式）。
- **教学班成员冻结**：教学班已被开课引用后，**不允许变更成员集合**（`ErrClassInUse`，HTTP 409），避免排课后成员变动导致课次归属语义错乱；改名/改备注仍可。删除被引用的教学班同理拒绝。
- **行政班引用保护**：删除已被教学班引用的行政班返回 409，需先从教学班移除。
- **教学班成员下限**：创建/更新教学班至少 1 个行政班成员（400）。
- **课次重叠约束（应用层）**：创建/更新课次与预约都检查「与任一课次区间重叠、或与任一 pending/approved 预约区间重叠」，且在教室行 `FOR UPDATE` 锁下进行，防并发插入；导入器同样做区间重叠预检。
- **教师必填**：开课的 `teacher` 必填（旧模型可空）。

## 5. 权限

行政班/教学班挂独立权限 `admin_class:read/manage`、`teaching_class:read/manage`（`admin` 通配，普通 `user` 角色仅可读）；课程本体沿用 `course:read/manage`。权限链与目录见 `internal/authz`。
